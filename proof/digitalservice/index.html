A small product/architecture proof for a recurring public-service problem: the same household evidence is collected repeatedly, while different rules need different income definitions. The hypothesis: separate canonical evidence from versioned rule projections — and make missing data and provenance visible by default.

01 / problem framing

The bottleneck is not another form.

A reusable service needs to know which facts exist, where they came from, whether they are current and verified, and how a particular rule treats them. The user should not have to understand that machinery.

One evidence layer

Payroll, maintenance and other evidence enter a canonical household packet with source and date.

Many definitions

Each service projects only the fields its versioned rule requires. Different definitions do not require recollecting everything.

Fail closed

Missing or unverified required evidence produces NEEDS DATA / REVIEW, never a confident invented amount.

03 / product invariants

What I would refuse to ship without.

Version visible

Every result identifies the rule version that generated it. Replays must remain possible after rules change.

Source visible

Every included fact retains provenance and as-of date. An explanation is not evidence.

No AI authority

AI can extract, classify or explain. The final numerical projection is deterministic and testable.

Missing ≠ zero

Unknown evidence is never silently treated as €0 when a rule requires it.

Reusable by design

A new rule should add a projection module, not another citizen data collection journey.

Measure the outcome

Track repeated evidence requests, processing time, clarification loops, error rate and successful reuse.

04 / discovery plan

What I would validate next as a Product Manager.

Hypothesis 1: a canonical evidence packet materially reduces repeated citizen input and manual validation.

Hypothesis 2: rule-specific projections make legal differences explicit enough for domain experts to review and maintain.

Hypothesis 3: showing missing/uncertain facts earlier reduces clarification loops downstream.

First research: 5–8 case-processing interviews + process mapping; compare the same income fact across two services; prototype with domain experts; measure time-to-complete, repeat requests and correction rate.

Scale question: which part belongs in a central basis service and which must remain service-specific?

05 / implementation proof

The UI is backed by tested invariants.

The repository contains a deterministic Python Income Kernel and tests for multi-definition projection, missing-data blocking, unverified-evidence review, provenance and rule-version visibility.
