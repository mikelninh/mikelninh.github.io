# ClaimsOps Reliability Loop · Independent INCA Work Sample

**Live application:** https://mikelninh.github.io/inca/reliability-loop.html

**Core question:** INCA already operates AI agents. How could an AI Operations Associate help make errors easier to investigate and less likely to recur?

This is a **working controlled simulation**, not a connection to INCA's MARS platform. Everything is developer-authored fiction: 12 cases, invented policy documents and agent traces, five deliberately planted structural failures. No real LLM calls, insurer data, coverage decisions, customer messages, payments, or human reviewer time. Explicit guardrails supplement—not replace—production controls.

## The 30-second hiring-manager experience

The page tells the whole story up front: **problem → independent check → repeat-error test**.

1. The fictional CASE-027 agent quotes real text from policy 2024, but the applicable version is 2025.
2. **Run the independent check** evaluates the recorded trace and blocks the next step for human review. This does not execute an external action.
3. **Replay saved fix & retest** replaces only CASE-027 with its developer-authored corrected trace; the six structural checks now pass. Four other deliberately faulty fictional traces remain blocked.
4. Optional **Bring back the mistake** reintroduces the old policy into that corrected trace, and the same gate blocks it again. This is the core "prevent repeat" demonstration.
5. Optional **engineering evidence** exposes the entire 12-case fixture set, six checks, source texts, and a clearly labelled action to load all five previously authored example corrections and retest. There is no requirement to click through four more mistakes.

The default 2-click path deliberately does **not** pretend to fix all five cases. The standalone technical evidence measures **5/5 known deliberately planted faults blocked** in 12 invented traces. No model is trained or automatically improved. Everything in the browser is client-side and ephemeral. Python implements the authoritative reproducible fixture generator and evaluator; Node tests assert equivalent outputs and the visitor path.

## Actual implementation

- [reliability.py](reliability.py): deterministic fictional case generator, six rule checks, comparison of pre-authored release A and release B, machine-readable report, stable dataset checksum.
- [test_reliability.py](test_reliability.py): unit and integration regressions for policy revisions, literal citations, missing sources, unauthorized actions, skipped verification, bounded gates and deterministic output.
- [reliability-loop.js](../../inca/reliability-loop.js): active six-check browser evaluator, state transitions, local correction/release staging, arbitrary fault injection and release-gate execution.
- [reliability-loop.test.cjs](../../inca/reliability-loop.test.cjs): browser/Python check parity across all 24 release snapshots, no false approvals and red/green re-injection tests.
- [reliability-loop-data.json](https://mikelninh.github.io/inca/reliability-loop-data.json): generated by Python **inside GitHub Actions**. It is not hand-invented browser output; Pages deploy includes the generated result.

Reproduce without any secrets or network calls:

\`\`\`bash
python inca-proof/reliability-loop/reliability.py --out inca/reliability-loop-data.json
python -m unittest discover inca-proof/reliability-loop -p 'test_*.py' -v
node --test inca/reliability-loop.test.cjs
\`\`\`

## What the results do and do not mean

| Measured on seeded fixtures | Result |
|---|---|
| Fictional traces | 12 |
| Deliberately planted fault types | 5 |
| Release A: blocked by deterministic gate | 5/12 |
| Release B: pass structural checks after **scripted** corrections | 12/12 |
| Known seeded critical escapes under this gate | 0/5 |
| New LLM API requests | 0 |

These are **fixture assertions**, not AI performance, real claim accuracy, deployment readiness, actual operating costs or human time saved. A test passing is permission only to *continue other mandatory checks*, not coverage/claim/payment approval.

The browser intentionally provides no storage, account system or side effects; it does not claim to create real persisted regression cases from user actions. The Python unit tests are the persisted technical learning artifact.

## What I would ask INCA before a real pilot

Which existing controls and trace IDs does MARS already have? What are the top recurring exceptions in the real operator queue? Can I access appropriately anonymized event metadata with permission? Which issue warrants a reproducible regression? What does a resolved case cost in human minutes? How does a proposed new gate change false positives, critical misses, service levels, human effort and system latency?

Start by listening and shadowing one bottleneck. Build only the smallest additional integration that existing operators and engineers say would help. No production automation based on synthetic pass rates.
